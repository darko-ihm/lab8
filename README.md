1. Статичний аналіз коду (SAST)
Для статичної перевірки використано два інструменти:

Bandit (профіль налаштувань у файлі .bandit з виключенням директорії venv) — спеціалізований сканер вразливостей безпеки Python.

Pylint — аналізатор якості, стилю та потенційних логічних дефектів коду.

Виявлені вразливості до виправлення (reports/before/bandit_before.txt)
OS Command Injection (B602, High, CWE-78): виклик subprocess.check_output(..., shell=True) з прямою підстановкою параметра host.

Flask Debug Mode (B201, High, CWE-94/CWE-489): запуск сервера з debug=True, що відкриває інтерактивний відлагоджувач Werkzeug.

SQL Injection (B608, Medium, CWE-89): формування SQL-запиту через f-рядок f"SELECT ... LIKE '%{query}%'".

Hardcoded Secret (B105, Low, CWE-798): жорстко закодований ключ сесій app.secret_key у вихідному коді.

Subprocess Import (B404, Low, CWE-78): інформаційне попередження про імпорт модуля subprocess.

2. Динамічний аналіз коду (DAST)
Додаток було запущено у режимі відлагодження та контролю ресурсів Python (python -X dev src\app.py) і проскановано під час виконання за допомогою власного DAST-сканера (dast_scanner.py) та утиліти curl.

Підтверджені проблеми під час виконання (reports/before/dast_before.txt)
[CRITICAL] OS Command Injection (/ping?host=localhost%26whoami): сервер виконав системну команду whoami і повернув ім'я облікового запису ОС.

[HIGH] SQL Injection (/search?q=%27%20OR%20%271%27=%271): зловмисник обійшов фільтрацію та витягнув прихований запис Admin Backup.

[MEDIUM] Відсутні HTTP-заголовки безпеки: у відповідях сервера були відсутні X-Frame-Options, X-Content-Type-Options та Content-Security-Policy.
 
 ### Порівняння методів SAST та DAST

| Критерій | Статичний аналіз (Bandit, Pylint) | Динамічний аналіз (DAST-сканер, `-X dev`) |
| :--- | :--- | :--- |
| **Принцип роботи** | Аналіз вихідного коду без запуску («біла скринька») | Тестування запущеного сервера HTTP-запитами («чорна скринька») |
| **Унікальні знахідки** | Виявив зашитий у коді `app.secret_key` та `debug=True` | Виявив відсутність захисних HTTP-заголовків безпеки |
| **Спільні знахідки** | Вказав на точні рядки з SQLi та OS Command Injection | Підтвердив реальну експлуатацію SQLi та OS Command Injection |

Обґрунтування критичної вразливості (OS Command Injection, CWE-78)
Чому небезпечна: вхідний параметр host із HTTP-запиту без перевірки передається в командну оболонку ОС через shell=True. Використання метасимволів (&, |, ;) дозволяє дописати довільну команду операційної системи.

Можливі наслідки: віддалене виконання коду (RCE) з правами процесу вебсервера, читання або знищення файлів сервера, викрадення ключів доступу та розвиток атаки на внутрішню мережу.

3. Рекомендації та впроваджені виправлення
У вихідний код src/app.py внесено комплексні виправлення:

Захист від Command Injection: додано валідацію вхідного параметра host за білим списком регулярного виразу ^[a-zA-Z0-9.-]+$, а виклик subprocess.check_output переведено на передачу аргументів списком із shell=False.

Захист від SQL Injection: конкатенацію рядків замінено на параметризований SQL-запит (WHERE title LIKE ?).

Захист секретного ключа: app.secret_key зчитується зі змінної оточення FLASK_SECRET_KEY або генерується криптостійко через os.urandom(24).hex().

Захист конфігурації: вимкнено режим відлагодження (debug=False) та додано middleware @app.after_request для встановлення заголовків X-Frame-Options: DENY, X-Content-Type-Options: nosniff і Content-Security-Policy: default-src 'self'.
